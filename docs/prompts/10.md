# FACoP Issue #10 — Prompt / Attempt Provenance

This file records externally shareable engineering provenance only. It intentionally does not contain hidden chain-of-thought or private scratchpads.

## Attempt 0001 — 2026-09-04

### Trigger

The maintainer changed the contribution model after reviewing Atomic Behavior Collaboration and FACoP security work:

- production code should not be accepted as the contributor's authoritative artifact;
- the contributor should provide the prompt/context and information that led to understanding the problem;
- the final authority for a defect claim is the contributor-authored executable test that proves the declared base fails;
- the project should evaluate that test directly, inject the same bytes into the `tests` profile, independently generate its own candidate, and require the candidate to make the unchanged test pass.

The maintainer named the proposed model **Validated Reason Development** and requested prior-art research plus implementation in FACoP.

### Research observations

Searches for the exact phrase `Validated Reason Development` did not identify an established software-engineering method under that name.

Closest reviewed work included:

- test-suite-based automated program repair (tests as executable repair oracles/specification approximations);
- TDFlow (EACL 2026), which explicitly frames repository repair as solving human-written tests and identifies reproduction-test creation as a major remaining bottleneck;
- recent Bug Reproduction Test research, including work showing that fail-to-pass alone can be too weak for total patch correctness;
- prompt-provenance research treating prompt/context lineage as first-class engineering artifacts;
- existing open-source reproducible-issue templates that accept executable failing cases.

No reviewed source combined the FACoP v0.2 authority rules: code-free contributor authority + contributor test as normative problem proof + prompt/context provenance + upstream-independent regeneration + unchanged control/treatment reproduction.

### Architectural correction

FACoP v0.1 modeled `PatchProduced` / contributor patch provenance as part of the contribution lifecycle. v0.2 changes the ontology:

`Contribution = Claim + ExecutableReproduction + ExpectedFailure + ReasonProvenance + Evidence`

The upstream owns candidate generation. ProblemProof and SolutionProof are distinct evidence objects.

### Implementation

The reference implementation adds:

- a code-free contribution guard;
- a Validated Reason proof library;
- a Git worktree-based reproduction gate that injects identical test bytes into base and generated-candidate trees;
- a dedicated `tests` profile/workflow;
- qualification consumption of the tests-profile proof;
- schema/lifecycle/profile updates;
- protected-path ownership for the new gates;
- integration tests for fail→pass proof, wrong-failure rejection and production-patch rejection.

### Security constraints

Contributor reproduction tests remain untrusted executable code. The reference reproduction runner constructs a restricted environment and does not forward credential-shaped process environment variables. Hardened adapters should add network/filesystem/process isolation.

### Result

The intended invariant is:

> The contributor proves the problem. The upstream proves the solution.

The contributor reproduction may become an upstream regression test only after independent reproduction and solution qualification.
