# Issue #1 — Prompt / Attempt Changelog

This file is append-only at the conceptual level. Sensitive information is excluded.

## Attempt 0001 — 2026-09-02

### Human intent

Create a scientific article and the complete technical documentation/reference pipeline for FullAgenticCollab/FACoP, reusing the AllasCode Everything-as-Code action pattern and demonstrating it with a small e-commerce domain (Users, Products, Consumers, Stock, Payment, Delivery).

### Architectural constraints extracted

- issue-first contribution;
- contributor local tests before remote CI;
- semantic `dev`, `stage`, `tests/qualification` profiles;
- contributor characterization limited to affected/new functions;
- upstream-owned unit/integration/E2E/security acceptance;
- all expensive historical evidence reusable when its complete semantic input set is unchanged;
- benchmark/load/stress/chaos serve as technical characterization as well as optional gates;
- no manual steps in the intended steady-state workflow;
- GitHub is an adapter, not the protocol definition.

### Result

Accepted as the bootstrap design. Implementation proceeds on `issue-1-bootstrap-fullagenticcollab-dev`.

## Attempt 0002 — 2026-09-02

### Trigger

The FACoP `stage` profile failed after contributor `dev` evidence had passed.

### Independent evidence

- Unit: 18/18 PASS.
- Integration: 5/5 PASS.
- E2E: FAIL before executing checkout because `CommerceState` was imported as a runtime ESM value although it is a TypeScript-only type.

### Correction

Change `checkout.ts` to use `import type { CommerceState }`, preserving all runtime imports separately.

### Why this attempt matters

This failure is evidence for FACoP's separation of contributor-owned action tests from upstream-owned acceptance tests: local/action-level validation did not observe the module-boundary failure, while E2E did.

### Result

Patch produced as commit `7a5d57504e3bf877cf1e17a30335942bf52a4049`; stage revalidated the repaired revision successfully.

## Attempt 0003 — 2026-09-02

### Trigger

The first qualification succeeded, but implementation review identified two gaps between the normative FACoP specification and the executable reference: Content-Addressed Evidence was calculated but not reused across qualification runs, and workflow dependencies were referenced by mutable major-version tags.

### Correction

- persist prior Evidence Passports as GitHub workflow artifacts;
- restore the previous passport during qualification;
- calculate a per-action EvidenceKey from action files, shared semantic/runtime inputs, validation policy, characterizer, qualification workflow and environment class;
- execute characterization only for EvidenceKeys that are missing or changed;
- reuse only records whose current EvidenceKey exactly matches;
- pin checkout/setup-node/upload-artifact by immutable commit SHA;
- disable persisted checkout credentials;
- document the GitHub adapter and direct AllasCode integration contract.

### Result

The hardened qualification restored the previous passport, correctly invalidated all 14 old records because their EvidenceKeys changed, and produced a new qualified passport.

## Attempt 0004 — 2026-09-02

### Trigger

Pre-main domain review found that successful checkout reserved stock but never consumed the reservation. The previous E2E expectation `{available:3,reserved:2}` represented an incomplete sale rather than a final inventory state.

### Correction

- add `Stock.commitStock` to consume a successful reservation;
- add `Payment.cancelPayment` for pre-capture compensation;
- change checkout to `reserve → create payment → authorize → create delivery → capture → commit stock`;
- compensate an owned failed checkout by cancelling/refunding payment as applicable, cancelling created delivery and releasing still-reserved stock;
- change E2E success to require `{available:3,reserved:0}`;
- add an E2E failure case proving payment cancellation and stock restoration when delivery creation fails.

### Result

This semantic change invalidates relevant source, E2E and characterization evidence and therefore requires a new complete FACoP promotion.

## Attempt 0005 — 2026-09-03

### Trigger

Specification review raised three rules that were stated in prose with no declared enforcement
point, each of which would invite a wrong implementation if left implicit:

1. `CONTRIBUTING.md` step 9 said "contributor CI validates changed/affected action evidence"
   without saying where that CI runs or under whose credentials. An earlier sketch had CI create
   the upstream Issue/PR automatically, which is the classic fork + `pull_request_target`
   escalation surface. The document did not say whether that had been removed from the design or
   merely left undocumented.
2. `PROVENANCE.md` said prompt logs must not publish secrets, with no mechanism. Because
   `docs/prompts/<ISSUE-ID>.md` becomes public and append-only, a rule enforced only by author
   discipline is decorative.
3. `CONTRIBUTING.md` step 11 said valid Content-Addressed Evidence may be reused, without saying
   who vouches for that validity. An EvidenceKey proves no semantic input changed; it does not
   prove the first execution was honest. `Attest` appeared in the lifecycle but had no mechanism.

### Correction

Added `docs/security-model.md` as the normative companion to `docs/spec/SECURITY.md`, and a
mechanical gate behind each of its three claims.

- Trust planes: contributor CI runs in the contributor's own repository/fork under that
  repository's own token; automatic upstream PR creation from contributor CI is removed from the
  design, stated as removed rather than omitted. `pull_request_target` and `workflow_run` are
  forbidden in every FACoP workflow. `scripts/workflow-guard.ts` enforces this plus
  no-write-permissions, no `${{ secrets.* }}`, `persist-credentials: false` and SHA-pinned
  `uses:`.
- Secret hygiene: `scripts/secret-scan.ts` at three positions — `scripts/hooks/pre-commit`,
  `scripts/hooks/pre-receive`, and a required CI check inside `test:stage` and `facop-dev.yml`.
  The scanner redacts its own matches so a public CI log never republishes what it caught, and
  rejects committed key material. The gate placement is normative; gitleaks/trufflehog
  substitute at the same positions.
- Attestation: a DSSE-style Ed25519 envelope over the Evidence Passport, signed by the plane
  that executed the evidence in the same job that produced it, verified against
  `config/trusted-keys.json` with fail-closed rejection of unknown, revoked, expired,
  wrong-profile and wrong-revision keys. `qualify.ts` refuses an unattested prior passport before
  the stage suite runs; the qualification workflow verifies on restore and re-verifies after
  signing against `GITHUB_SHA`.

### Evidence

`tests/integration/security-controls.test.ts`, 16 cases: tampered payload under a trusted key,
unknown key, revoked key, expired key, profile confusion, unattested reuse, scanner block and
pass, and a per-file assertion that no workflow uses `pull_request_target`. Full `test:stage`
passed (unit 21, integration 16, e2e 3). The pre-commit hook was verified against a staged
credential-shaped literal: the commit was rejected and `HEAD` did not move.

### Known residual

`config/reference-attestation-key.pem` is a non-production key with a deliberately public private
half, present only so this repository can self-test reuse across executions. A real deployment
removes it from `config/trusted-keys.json`. The trust root is a file in the repository, so
whoever can merge a change to it can add a producer; that control is organizational, not
cryptographic. Both are stated in `docs/security-model.md` §4.

### Result

The three rules are now enforced rather than asserted. No secret, key or credential is recorded
in this changelog; the attestation key id is public by construction.
