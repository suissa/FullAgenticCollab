# FullAgenticCollab

FullAgenticCollab is an open initiative for reproducible, evidence-driven collaboration among humans, AI agents and software projects.

The normative specification is **FACoP — Full Agentic Collaboration Protocol**.

## Validated Reason Development

FACoP v0.2 introduces **Validated Reason Development (VRD)**: a collaboration model in which the contributor does **not** contribute production code for upstream acceptance. The contributor contributes a falsifiable reason for change.

For a defect contribution:

`Contribution = Claim + ExecutableReproduction + ExpectedFailure + Prompt/Context Provenance + Evidence`

and explicitly:

`Contribution != Patch`

The central rule is:

> **The contributor proves the problem. The upstream proves the solution.**

The executable reproduction is the normative authority for the defect claim. Prose explains the claim; prompt/context provenance explains how it was formulated; neither substitutes for the executable proof. Contributor-produced production code is not an acceptance artifact.

### Two-sided executable proof

Let `B` be the canonical base, `R` the contributor reproduction, `P` the claimed failure identity and `Cᵤ` a candidate independently generated by the upstream plane.

A problem is proven only when:

`R(B) = FAIL(P)`

A solution is proven only when the **same reproduction bytes** satisfy:

`R(B + Cᵤ) = PASS`

with:

`hash(R_control) = hash(R_treatment)`

A test that passes on the declared base, fails for a different reason, or changes between the control and treatment cannot establish the FACoP proof.

### Why the `tests` profile exists

The GitHub adapter materializes the causal comparison on an `*-tests` branch. The upstream pipeline creates isolated worktrees for the canonical base and the upstream-generated candidate, injects the contributor's reproduction into both, and records machine-readable `ProblemProof` and `SolutionProof` evidence.

The contributor test is untrusted executable input. It runs without upstream mutation credentials or secret-bearing environment variables. Once the generated solution is accepted, the exact verified reproduction MAY be promoted to an upstream-owned regression test.

## Why

Agentic software development makes generated implementation code abundant and replaceable. What remains expensive is stating the correct problem, producing an executable oracle that demonstrates it, preserving the prompt/context that led to that understanding, and independently verifying a generated solution.

FACoP therefore shifts collaboration from **patch transfer** to **validated problem transfer**. A project need not trust the contributor's implementation because it can regenerate its own candidate from the validated claim, repository context and safe provenance artifacts.

## Lifecycle

`Issue → Claim → ReproductionSubmitted → ProblemProven → ReasonValidated → IndependentRegeneration → CandidateGenerated → SolutionProven → Characterize → Validate → Attest → Qualify → Propose → Review → Observe → Repair → Accept`

The implementation MAY collapse adjacent states, but it MUST preserve the distinction between proving the problem and proving the independently generated solution.

## Execution profiles

FACoP models:

`local → dev → stage → tests → qualification → upstream`

- `local`: contributor feedback on the contribution package and reproduction.
- `dev`: code-free contribution guard, provenance/secret checks and portable contributor evidence.
- `stage`: upstream generation/integration environment and upstream-owned acceptance suites.
- `tests`: causal control/treatment proof using the unchanged contributor reproduction.
- `qualification`: evidence closure and attestation.
- `upstream`: canonical proposal, review observation and final decision.

Branches are only adapter materializations. The normative identities remain the contribution, base revision, generated candidate revision and evidence digests.

## Evidence rule

An expensive test is not rerun merely because a pipeline started. It is rerun when its `EvidenceKey` changes. For VRD, the reproduction digest, base revision and generated candidate revision are first-class evidence inputs.

Qualification means **prove that valid evidence exists for every required property**, not blindly execute every historical test.

## Research position

A literature and ecosystem search performed on 2026-09-04 found no established software-engineering term exactly named **Validated Reason Development**. Several adjacent lines of work are important prior art:

- test-suite-based automated program repair uses tests as executable approximations of specifications;
- **TDFlow (EACL 2026)** explicitly frames repository repair as solving human-written tests and argues that accurate reproduction-test creation is the remaining bottleneck for autonomous repair;
- bug-reproduction-test research studies fail-to-pass reproduction signals and their limits;
- prompt-provenance research treats prompts and context lineage as first-class engineering artifacts;
- reproducible bug-report workflows already ask contributors to provide executable failing cases.

The distinction claimed by FACoP is narrower: in the sources reviewed, we did not find an open collaboration protocol that simultaneously (1) rejects contributor production code as the contribution, (2) makes the contributor-authored executable test the normative authority for the problem claim, (3) preserves prompt/context as contribution provenance, and (4) requires an upstream-controlled independent regeneration whose candidate is validated by the unchanged test. See [`docs/research/VALIDATED-REASON-DEVELOPMENT.md`](docs/research/VALIDATED-REASON-DEVELOPMENT.md).

## Reference example

The e-commerce example contains six entities: Users, Consumers, Products, Stock, Payment and Delivery. Each behavior follows the AllasCode-style independent action structure with README, manifest, config, schema, events, implementation and tests. Under VRD those implementation files are produced by the upstream generation plane; they are not accepted from a problem contributor.

## Status

Experimental specification, **v0.2.0**. VRD is normative for problem contributions in the reference model; autonomous acceptance remains subject to the protected-path and trust controls defined by FACoP.
